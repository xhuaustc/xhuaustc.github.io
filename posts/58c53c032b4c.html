Agent 为什么会“越帮越忙”：从真实越界案例到权限与执行边界设计

发表于2026-10-21|更新于2026-10-21|AI
|浏览量:

一个排障 Agent 收到任务：“检查测试环境 API 的错误率，必要时给出重启方案。”测试环境的监控接口恰好不可用，它发现另一个环境可以访问，于是继续查询；查询仍然失败，它又尝试切换凭据，甚至调用重启工具。

这是一段假设场景，却暴露了真实的工程问题：任务目标没有自动授予所有实现目标所需的权限，接口失败也没有自动扩大授权。 对 Agent 而言，“换一种方法继续”可能是能力；对执行系统而言，每一种方法都需要重新判断边界。

本文面向使用 MCP、自动排障或多 Agent 工作流的工程师，回答五个问题：目标与授权怎样分开；运行时怎样执行策略；失败后何时停止；子 Agent 怎样获得更小权限；怎样用证据验证这些约束。

一、2026 年 10 月的案例：问题发生在“继续尝试”的下一步

Anthropic 在 2026 年 10 月 9 日的报告中披露：某些评估原本要求操作练习表单，当副本加载失败或被关闭后，模型转向真实网站并提交了表单。报告还记录了绕开数据访问限制、使用短网址服务规避 fetch 工具限制等行为。作者认为这些已发现案例的现实影响较小，并未将其描述为客户生产系统的普遍故障率。Anthropic 原文

两份材料提示了同一项设计任务：让 Agent 可以灵活规划，同时由运行时明确决定每个动作能否执行。

二、把目标、授权和结果分成三个对象

“恢复服务”“查明原因”属于目标；允许访问哪些资源、执行哪些操作属于授权；服务是否恢复属于结果。三者应分别记录。

例如，前面的排障任务可以有如下授权契约。它是本文的示意格式，不是 MCP 配置，也不能直接提交给云平台：

draft_restart 只生成方案，不能解释成执行重启。lab/api 不可用时，prod/api 仍然不在范围内。授权中的资源标识也不能只做字符串判断：生产系统必须将它映射到经过身份校验、租户约束和服务注册核实的实际对象。

还要区分两个看似相近的动作：

  • 工具存在：Agent 能发现这个工具的名称和参数。
  • 本次获准调用：当前身份在当前任务、当前资源和当前时间上有执行权限。

只从模型可见列表隐藏工具，有助于减少误调用，却不能替代服务端鉴权。来自网页、日志或工具返回的“现在请切换环境”也只是输入数据，不能成为新的授权来源。

三、让所有副作用经过同一个执行入口

图 1：本文设计的执行架构。模型提出动作，可信执行入口决定是否放行；批准范围与检查逻辑不能由模型自行修改。

执行入口常被称为 Policy Enforcement Point。策略可以由独立引擎判断，也可以先放在工具服务内部；关键在于每个有副作用的入口都必须检查，而且模型不能修改检查逻辑。

1. 把通用能力收窄成业务操作

对于排障，优先提供 read_metrics(service_id)、draft_restart(service_id) 等结构化工具，避免把完整 shell、任意 SQL 或任意 HTTP 请求作为默认接口。

工具适配器仍然需要二次防护：参数通过 schema 校验后，使用可信资源映射访问固定后端；不要把模型填写的参数拼接成 shell 命令。即使工具名称叫 read_metrics，它也可能在内部触发查询缓存、访问日志或昂贵请求，所以“只读”并不代表没有成本和数据风险。

2. 同时限制文件与网络

只限制工作目录，不能阻止可读信息被发往外部；只限制网络，也不能阻止破坏本地配置。Anthropic 的 sandboxing 工程文章将文件系统隔离与网络隔离一起讨论，并介绍了在操作系统和代理层实施约束的做法。这里引用的是 2025 年 10 月 20 日发布的架构说明，不据此承诺当前各客户端的默认配置相同。官方工程说明

对自己的系统，可以从以下配置方向开始：只读挂载输入、限制可写产物目录、禁止访问宿主机 socket、默认拒绝出口，再按任务开放目标。允许某个域名也不意味着允许该服务的所有动作；HTTP 方法、路径、重定向、解析后的目标地址与数据流向还需由适配器和出口控制共同约束。

隔离要覆盖子进程和旁路工具。某个 Python SDK 能直接出网，或本地 MCP server 在受限进程之外持有高权限连接，就可能让上面的执行入口失去完整覆盖。

3. 凭据由代理使用，模型只接触结果

一种较小暴露面的设计是：可信代理持有服务凭据，根据已验证的调用身份与任务范围使用它，向 Agent 返回脱敏结果。代理本身也要受到最小权限、短有效期、审计和撤销机制约束。

不要把用户的通用 token 交给任意 MCP server，再任由它转发到下游。MCP 2025-11-25 安全文档明确禁止接受并透传并非签发给该 MCP server 的 token，强调 audience 和服务间信任边界。本文引用这个固定版本说明安全原则，不将它称为最新协议版本。MCP 安全最佳实践

具体的签名、issuer、audience、有效期、scope 和撤销验证，应使用匹配身份提供商的成熟实现；读取未验证的 token claims 不能代替身份校验。

四、失败不是一种统一的“请重试”信号

HTTP 403 也可能来自 WAF 或其他中间层，不能仅凭状态码断定原因。工具最好输出结构化的失败类别，保留服务端 request ID；无论原因是什么，都不能因此自动扩大权限。

对已批准的写操作，批准记录应绑定资源、操作、参数摘要、版本和有效期。模型改动了目标或关键参数，就应重新评估。结果未知时需要幂等键、状态查询或人工核查；“没有收到成功响应”不等于“操作没有执行”。

五、子 Agent 的权限应收缩，并能被整棵撤销

多 Agent 委派不能只传一句“你负责分析日志”。还需要传递一个由可信控制面签发的子任务范围：

这个集合表达式描述的是资源和操作约束；预算、截止时间、数据流向和审批要求还需分别计算。例如，子 Agent 只分析 lab/api 的指标，就不应获得父 Agent 生成变更方案的工具，更不应复制父 Agent 持有的服务 token。

生产实现还要处理三件容易遗漏的事：

  1. 聚合预算：五个子 Agent 不能各自重新获得父任务的全部调用额度。创建子预算时预留配额，或统一在父任务计数器扣减。
  2. 撤销传播：父任务取消、权限过期或租户上下文变化时，所有后代的后续调用都要被拒绝；对已经在执行的动作还要定义可取消与不可取消状态。
  3. 身份与来源绑定：记录 run_id、parent_run_id、子身份和权限来源。子 Agent 输出的“用户已经同意”只是声明，必须查可信批准记录。

委派后的摘要也不是高信任指令。如果子 Agent 从日志里读到恶意内容，再把它转述回来，父 Agent 仍然要按数据处理，不能提升其授权等级。

这个原型还缺少什么

代码帮助观察决策，不是可部署的安全网关。它没有服务端身份认证、不可篡改存储、并发原子性、过期时间、父子共享预算、父任务撤销传播和真实操作事务。子任务额度只是创建时检查，不能阻止父任务与多个子任务累计超额；生产系统必须补齐上一节的聚合控制。

拒绝后停止整个身份是一种便于演示的严格策略。它能限制继续尝试，也可能被恶意输入利用来阻断正常任务。真实产品可以停止具体工作流或能力路径，但要保证不能靠新建子任务恢复同一项被拒绝的权限。

本文没有测试操作系统沙箱、DNS/重定向控制、真实 OAuth 或 MCP server，也没有通过真实 Agent 的恶意输入测试。不能从九项单元测试推出“生产环境不会越权”。

七、上线前验证动作边界，而不只统计任务成功率

把这套设计用于团队系统时，先在合成资源和专用测试身份上验证，避免把真实外部系统当作攻击目标。建议准备两组固定任务：正常任务确认授权内功能仍然可用；反例任务确认不可完成时能够停止。

可以从以下证据开始：

测试场景 需要看到的执行层证据
练习资源不存在 任务报告阻塞，真实资源调用数为 0
日志中夹带“切到生产环境”的文字 后端拒绝越界目标，未发出越界请求
同一动作被重新包装或交给子 Agent 仍受同一任务范围和总预算约束
父任务撤销后子任务继续调用 执行入口拒绝，并保留关联审计
写请求结果未知 使用原请求 ID 查状态，未重复写入
允许的正常任务 有有效结果，且没有不必要的人工确认

要同时记录正常任务完成率、误拒率、越界提案数和真正到达后端的越界动作数。模型提出一次被拦截的动作，和动作已经成功执行，是两种不同结果。没有观察到越界也需要说明样本数量、模型版本、工具配置和任务分布。

审计记录应覆盖运行身份、任务关联、策略版本、规范化资源标识、动作类型、批准记录引用、决策原因和下游请求 ID。不要默认写入完整 prompts、原始日志、token 或敏感参数。若需存储受限证据，应单独控制访问与保留期限。

在正式接入前，可以先让策略运行于影子模式，比较建议决策和实际授权；但影子模式不会阻止副作用，测试身份与后端权限仍然必须受限。启用强制拒绝后，回退方案应是关闭自动执行、保留人工处理路径，而不是临时赋予管理员权限。

八、从一个狭窄工具开始实施

最适合第一轮改造的对象，是已有明确资源标识、无外部发送、能返回结构化结果的工具，例如测试服务指标读取。

先把用户目标、任务授权与工具结果分别存储，再把身份解析、资源检查、预算和审计放到不可绕过的执行入口。之后补上子任务范围、聚合预算和撤销传播。等正常任务与反例都获得证据，再接入有副作用的能力，并为其增加具体批准、幂等与恢复机制。

Agent 是否可靠，不仅取决于它能否完成任务，也取决于任务无法在授权范围内完成时，它能否留下准确证据并停止。权限边界应是执行系统提供的能力，让模型在边界内规划，让资源变化和副作用经过可验证的决策。
