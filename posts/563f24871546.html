Codex Subagent 入门：用三个角色完成一个小任务

发表于2026-10-21|更新于2026-10-21|AI
|浏览量:

想学习多 Agent 协作，可以从一个很小的任务开始：让 Codex 实现购物车总价函数，依次交给三个角色做需求分析、代码实现和独立验证。

这个任务用一个 Agent 也能完成。拆成三个角色，是为了看清楚如何定义职责、传递结果，以及在发现问题后返回修复。

本文整理自一次 Codex 学习会话中的购物车示例，并按 2026 年 10 月 21 日查阅的官方文档核对配置。原会话只展示了方案，没有实际运行这三个 Subagent；下面也不把教学示例当作已经跑通的结果。

先看三个角色怎样协作

主 Agent 接收用户需求并协调流程，三个 Subagent 分别负责：

  • analyst：明确输入、输出和验收用例。
  • implementer：按方案修改指定文件，并运行测试。
  • verifier：对照原始需求检查实际代码、补查边界，并独立运行测试。

下图中的箭头表示主 Agent 安排的执行顺序，每一阶段完成后才开始下一阶段。三个角色之间的交接由主 Agent 组织。

    flowchart TD
    M["主 Agent 接收需求"] --> A["analyst：分析与验收用例"]
    A --> I["implementer：实现与测试"]
    I --> V["verifier：独立验证"]
    V -->|通过| D["主 Agent 汇总交付"]
    V -->|有问题| F["主 Agent 整理修复项"]
    F -->|最多两轮修复| I

Codex 支持按明确请求或适用的项目指令调用 Subagent，并由主 Agent 等待和汇总结果。这里选择串行流程，是因为实现依赖分析，验证又依赖实现。官方 Subagents 文档

怎样确认协作真的发生了

观察客户端中的 Subagent 活动和各角色结果，而不仅是最终回复里出现三个角色名。桌面客户端可以从主聊天中的活动记录打开子 Agent 查看工作；支持该功能的 CLI 可以用 /subagents 查看。查看 Subagent 活动

一次完整交付应能回答：三个角色是否实际被调用？implementer 修改了哪些文件？verifier 是否独立读代码、运行测试？还有哪些需求没有覆盖？

如果角色没有被识别，先核对文件位置、TOML 格式和 name，确认当前客户端已加载这些角色、项目允许委派且没有禁用 agents。不要把主 Agent 模拟的角色对话当作调用成功。

本例的 TOML 语法已做本地解析检查，文章也经过 Hexo 构建；三个自定义角色的加载、委派及购物车代码测试，未在当前环境验证。
